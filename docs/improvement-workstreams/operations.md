## Remaining external verification and intentional boundaries

- Test creator one-time and recurring checkout separately from platform plans/credit packs with configured Stripe test accounts; then verify signed webhooks, receipt/invoice availability and provider portal cancellation. Express wallet/local currency eligibility depends on actual browser/account/provider support.
- Test owner refund review/confirmation in Stripe test mode including refund notifications and signed refund delivery before production release. This work never executed a real refund. Historical or renewal charges whose provider metadata cannot be matched are blocked and need provider/platform review.
- Verify transactional sender, canonical origin and workers in deployed configuration; configuration readiness does not certify inbox delivery.
- Verify real Google/Zoom calendar conflict, reschedule and meeting confirmation using configured test connections. Simulated service preview does not exercise those providers.
- Checkout recovery has actual reviewed activation, qualified worker enrollment, send-time checks and logs in code. Its deployed sender/worker configuration and real provider acceptance are unverified; no sequence was activated or email sent in a live account. Broad affiliate launch remains deferred by the approved plan.
- The saved audience segment is a dynamic filter/review/export affordance. Existing automation delivery continues to enforce execution-time consent; there is no new bulk enrollment action for old contacts.

## Primary provider references used for refund behavior

- [Stripe — Create a refund](https://docs.stripe.com/api/refunds/create): original charge/payment identity, refundable amount and optional application-fee treatment.

- [Stripe — Refund object/status](https://docs.stripe.com/api/refunds): pending/succeeded/failed outcomes remain distinct from a successful HTTP request.
